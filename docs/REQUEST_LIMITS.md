# Shop request limits

Published configuration: contact 5, checkout 20, withdrawal 10 attempts per ten-minute window per hosting-provided IP and route. No CAPTCHA, browser storage or external challenge provider. Stripe webhooks and GET pages are excluded. These are application limits, not comprehensive DDoS protection; shared IPs share a budget and IP rotation can evade it.

`shop_take_request_slot` is an atomic Postgres upsert accessible only to service_role. Anonymous and partner accounts cannot read counters or execute the function. Counters contain keyed HMAC identifiers, no plain IP. Expired rows are lazily removed (up to 100 per call); ten minutes is the enforcement window, not a guaranteed physical deletion deadline. A key rotation resets all client buckets.

Requires existing SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY; production expects VERCEL=1 and the platform-owned x-vercel-forwarded-for header. Never fall back to caller-supplied IPs. Failure or missing trusted identity returns 503 / Retry-After 30; limit exhaustion returns 429 with remaining seconds. Alternative email is displayed for form availability. No requests are silently dropped as successful.

Verification: mocked store allow/deny/outage/malformed responses, header trust, IPv6 normalization, separate route budgets and webhook exclusion; database transaction checks limit and expiry reset with rollback; privilege inspection. No real payment or email is generated by tests.
